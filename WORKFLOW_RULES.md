## Mandatory workflow reload protocol

1. Before a new task, resumed session or context reset, read this file (WORKFLOW_RULES.md), project-state.json and ../series/series-registry.json from disk. Then read the selected series bible, continuity and latest approved episode script. Do not infer current rules or story facts solely from chat memory.
2. Before changing production phase, reread the current policy/profile and the relevant phase documents in the reading table below. Refresh saved progress and the approved script when they affect that phase. A script, image or video task must use the corresponding current records.
3. If the user changes the workflow or a relevant instruction file changes, reload it and its controlling policy before dependent work. Resolve conflicts through R01; preserve the user's latest instruction.
4. Before export or final handoff, run the canonical rules check and the selected manifest QA. Resolve failures before export. A passing check verifies declared structure; it does not prove that an agent read the rules or that generated media passed review.
5. Never report that documents were read or checks passed unless those actions actually occurred. Agents working from compatibility folders must load these live shared files, rather than treating old pointers or archived rules as production policy.

## R02 — Resume and production sequence

Read project-state.json and the relevant registry entry, then the selected series bible, continuity and episode script. Respect active/completed/postponed organization; do not resume archived work just because an old guide names it. Page setup is conditional on missing settings or a requested change.

Sequence: concept → premise/script → series facts and storyboard → image queue → scene images and review → video prompts → generation and media review → edit → final package → authorized publication. Continuations must use approved facts, unresolved threads and existing character references. Runtime and scene count follow the deliverable; no universal 30-scene, 30-second or 150-second minimum.

## R03 — Script, performance and continuity

Write natural spoken Tagalog/Taglish appropriate to each character and situation. Give lines intent, context and emotional progression. Betrayal, status reversal, hooks, cliffhangers and micro-beats are creative options, not mandatory plot recipes or guaranteed viral results. Avoid repeating the same family premise, slang and ending across series.

Before image review or prompting, read the latest approved episode script and create a beat-by-beat emotion map: active character, intended emotion, visible expression/body language and continuity. Compare actual images to that map; use a neutral face only when the beat calls for one. Retain superseded candidates in old_draft_images/ or the existing draft archive.

Lock exact approved dialogue before generation. A rewrite, omitted line or changed meaning needs approval under the existing task authorization. Character identity references and textual traits supplement each other; descriptive “DNA tokens” cannot replace actual images. Lock face, hair, wardrobe, accessories, props, positions, eyelines, handedness, lighting and action state within a continuous scene. Plan wardrobe for timeline and setting changes; document intentional same-outfit continuity.

## R04 — Beat-based ingredient coverage (Unified Tagpi baseline)

Ingredients follow actual narrative beats, not a duration quota. A 4/6/8/10-second source may use one dedicated ingredient for one approved continuous performance, or two/three ingredients for distinct chronological beats. One-reference 10-second clips are valid. This supersedes the earlier duration-only 2–3-image quota under the user's latest adoption of the Tagpi baseline.

A distinct speaker turn, critical evidence insert or punch reaction needs dedicated coverage. Consecutive same-speaker speech may form one approved continuous block without changing words or order. One ingredient may support multiple angles of that same block, with at least two distinct shots and uninterrupted audio. Do not reuse a generic frame across unrelated lines or characters. Offscreen voice-over can use the visible listener's dedicated scene image with explicit speaker/subject mapping and closed visible mouths. Reconcile the inventory against the full script before approval.

## R05 — Filenames, attachments and mentions

Default scene filename: Clip [Number] - [Clean Descriptive Action or Subject].png. The unified Tagpi convention also accepts its chronological 1st/2nd/3rd Reference label before the descriptive words (`Clip [Number] - 1st Reference - [Clean Descriptive Action].png`). No series acronyms, episode IDs, technical abbreviations or shot codes in scene filenames. Keep internal IDs in metadata.

Every video beat, camera transition and spoken turn must explicitly anchor to its actual image filename with @Clip X - Exact Image Name, without .png. Preserve declared names and actual approved legacy names exactly. Set explicit mappings; never infer speaker identity from list position. A mention does not upload a file or guarantee fidelity.

## R06 — Merge planning, source duration and final edit

Merge compatible consecutive visual actions into a 4-second source (such as arrival → house reveal or door push → shocked eyes), and merge short action prefixes with dialogue (such as walking, entry, or prop-drop setup) into 6/8/10-second sources when chronology, available time and continuity permit. Allocate delivery time after the prefix; do not shorten or rush the approved line to make a merge fit.

Select 4/6/8/10-second tiers from measured/planned delivery plus the prefix. Spoken sources use 6/8/10; pure visual actions default to 4; a longer intentional silent hold needs an explicit duration reason. Approximately 3.5 syllables/second is an initial planning estimate from Tagpi, not a guaranteed natural speed. If speech needs more than 10 seconds, split naturally at a narrative boundary rather than rush or omit dialogue.

Source tiers are whole seconds, while approved internal beats, edit trims and audio bridges may use precise fractional timing (including a 1.50s prefix). Keep contiguous valid boundaries, exact assembled runtime and full audio coverage/order. A final evidence insert is distinct from generating an entire source; use the duration the story needs. Preserve approved lines, critical reactions, and evidence through the final edit.

## R07 — Framing and prompt construction

Use vertical 9:16. Choose camera angle, lens, depth and movement for the dramatic purpose; an 85mm lens or f/1.8 is an option, not a universal lock. Keep face/mouth clear during speech, a stable screen axis and legible evidence. Stable framing or a subtle motivated move is acceptable.

Character identity and scene population lock: Every Veo/Google Flow prompt, including plain-text directions and JSON handoffs, must explicitly preserve the exact character identity from each beat's @mentioned approved scene reference: face, age, skin tone, hair, body proportions, wardrobe and accessories across motion and camera cuts. Do not replace, duplicate or morph the referenced character. Declare who is visible in each beat and whether the approved scene requires background people. When it requires none, explicitly request no additional characters, extras, bystanders, crowd, silhouettes or people behind the speaking person, including blurred figures and people in reflections. When the scene requires another character or a crowd, explicitly name or describe the required people, their positions and actions; preserve that approved staging and add no unrequested people. An offscreen speaker remains offscreen unless an approved beat brings them into view.

One-image multi-angle standard: Every source using only one ingredient must have at least two explicitly planned camera shots with distinct angles (such as a medium shot cut to a close-up); preserve that same dedicated ingredient through its speaking interval. Angles of one performance do not need additional images merely to satisfy a count. Do not force exaggerated zooms or handheld shake. Use purposeful POV with a named owner and evidence coverage when the story calls for them.

The video scene-direction string starts with its actual timestamp, for example [0.00-6.00s]. Put character, time-of-day, location, action, exact image mentions and speech inside that timed direction; no unrelated prose before it. This applies to the string inside a serialized JSON prompt, not to the JSON object's opening character. Clip ordering belongs in filenames/manifest metadata. A prompt prefix does not guarantee downloaded filenames or suppress generated text.

## R08 — Continuous audio, voice-over mapping, pronunciation and content repair

Generation audio uses approved spoken dialogue/voice-over and diegetic sound only. Request no generated music, titles, subtitles or watermark; add approved music/branding in post. Maintain natural Filipino pronunciation and accent without caricature.

Continuous Audio: Every multishot source uses ONE continuous audio performance across visual angle cuts: never restart, repeat, mute, fade or interrupt a spoken line at a camera transition. If a provider cannot deliver that, reject the result and retain/bridge the complete reviewed audio in editing; do not approve interrupted speech.

Explicit Voice-Over Mapping: For offscreen dialogue, explicitly identify the actual speaker and the visible listening character separately in prompt and metadata. The listening character's dedicated scene image carries that offscreen line; visible mouths must remain closed (`visible_mouths_closed: true`). Do not animate a listener as if they spoke. Inner monologue also keeps visible mouths closed.

Scenes involving minors must remain age-appropriate and non-exploitative; use accurate neutral framing and describe the actual scene rather than relying on token substitutions. Do not claim a wholesome wrapper or clearing an upload tray guarantees acceptance. Any safety repair follows the same recorded revision and continuity review process.

Preserve canonical script spelling. The phonetic dictionary is a candidate pronunciation aid: apply only a reviewed, meaning-preserving pronunciation variant to the spoken field and record its canonical counterpart. Do not alter every technical/action field automatically. Respelling, image flipping/cropping, or substitute words are not a filter-bypass workflow. If a provider refuses a scene, record the refusal, address actual problematic content with a compliant revision, and obtain approval if dialogue, story meaning or continuity changes. Do not claim knowledge of provider caches or guaranteed acceptance.

## R09 — Authorization, clean batches, image folder standards, and failure handling

Use real, recorded authorization for the storyboard, declared image batch, video batch and publication. Existing authorization covers the same scope; do not ask again at every image. New scope or changed approved content needs appropriate authorization. Approval flags need evidence and actual reviewed output paths; never fabricate completion. Current manifests bind each batch authorization to a content scope hash. Reuse authorization for unchanged scope; changed scripts, mappings, pronunciation evidence, prompts or reviewed files invalidate the relevant authorization.

Standard Image Folder Policy: Whenever GPT or automation generates scene images, save them STRAIGHT and DIRECTLY into the episode's standard root folders: `images/` (containing all episode scene images) and `4seconds/`, `6seconds/`, `8seconds/`, `10seconds/` at the episode directory level. Never hide images exclusively in nested subdirectories (like `reference-images/`) while leaving root standard folders empty.

Clean Veo Import Batch Standard: To maintain clean episode folders and prevent attachment slot conflicts, generate video automation import files exclusively grouped by reference count (`veo-auto-1ref-<tier>-batch.txt`, `veo-auto-2ref-<tier>-batch.txt`, and plain reference prompts). Do not create redundant mixed duration-only files (`veo-auto-4s-batch.txt`, `veo-auto-6s-batch.txt`, etc.). Keep identity masters separate in `characters/` or `character-references/`. Preserve approved legacy layouts. Import objects and attachment slots must match; confirm a small authorized import before assuming a runner works.

Record failures, actual download paths and completed job IDs; resume pending work without duplicates. The local tracker records claims, actual downloads, hashes, continuity review and failure reasons. Claims are idempotent for running items and cannot restart completed items. Default retry limit is three attempts (configurable 1–10); retries require retained failed-output archives. Stop and report a repeated blocker instead of infinite silent retries. Unattended/background operation is a tested capability, not something granted by an “autopilot” instruction. Keep drafts and rejected outputs unless deletion of identified files is explicitly authorized; replacing an approved image does not authorize deleting its source.

## R10 — QA and publication

Review actual images and videos for line-to-image coverage, exact mentions, identity, emotion, lip movement, approved dialogue, costume, props, axis, chronology, timing, hands, evidence readability and unwanted text/music. Repair only failed scenes and recheck affected continuity. Model instructions describe targets; they do not guarantee zero drift, perfect voices or virality.

Check actual visible cast and background population against each approved beat under R07. Reject added people in a scene that requires no background people, identity substitutions/duplicates, and crowd or supporting-character changes that contradict required staging.

Final package includes the assembled movie and approved caption, cover/poster, music and branding as requested. Publish only within explicit authorization. Capture actual audience evidence separately from creative hypotheses. Never treat an example's performance or an unlinked claim as proof of causal reach.

## R11 — Thumbnail title and episode label integrity

For every new series or episode thumbnail, record the exact approved display title and the intended cover type before rendering. An episode cover must show `EPISODE N` in uppercase, where N is the actual episode number (`E001` → `EPISODE 1`, `E002` → `EPISODE 2`). Do not substitute `BAHAGI N`, `PART N`, or another label unless the user specifically requests that wording. A full-series cover uses the approved compilation label and has no episode number. This rule changes only future work and specifically corrected covers; preserve approved historical thumbnails unless the user requests a change.

Generate clean poster artwork without lettering, then add the exact title and episode label in an editable deterministic layout. Do not depend on the image model to spell or number the final thumbnail. Before delivery, compare the rendered PNG with the recorded title and cover type, visually inspect every cover at full size and small mobile size for spelling, number, crop safety and readability, and archive superseded renders. A text instruction alone is not proof that the pixels are correct.
